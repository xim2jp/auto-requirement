# RFP 分析の手順（RFP → RFP-NNN 分解 → 要件定義への写像）

Phase 1（RFP 分析）で requirements-architect が行う、**発注者の RFP を要件定義の上流として確定させる手順**。成果物は `docs/01-rfp/rfp-analysis.md`（テンプレ：`templates/rfp-analysis.md`）と `docs/00-inputs/INDEX.md`（テンプレ：`templates/inputs-index.md`）、初版の `docs/03-requirements/open-questions.md`。Phase 2 では対応 ID を後埋めし、Phase 3 で requirements-reviewer が判定基準に使う。project-manager は案件概要・文書セット・優先質問をユーザーと確認する材料に使う。

> IPA『ユーザのための要件定義ガイド 第2版』は「経営レベルの目的・目標・施策は企画工程で決まっているべきで、要件定義では**確認**する」とする。本ハーネスでは発注者の企画工程の結論が RFP であり、RFP 分析がその「確認」に当たる。

## 1. 入力と役割

| 入力 | 置き場 | 役割 | 扱い |
|------|--------|------|------|
| RFP 本文 | `docs/00-inputs/`（md／docx／xlsx／pptx／pdf） | 発注者の目的・要求・制約・提出物の一次情報 | **要件定義の上流（正本）**。原本は書き換えない |
| RFP 別紙・添付資料 | `docs/00-inputs/`（`materials/` を含む） | 現行業務・現行システム・帳票・規程・数量 | 本文の補足。食い違いは OQ |
| 参考資料・議事録 | `docs/00-inputs/` | 背景・経緯・口頭の要望 | 根拠として引用。RFP と食い違えば OQ |
| 抽出テキスト | `docs/01-rfp/extracted/` | Office 原本の機械抽出（`bash .claude/skills/office-deliverables/scripts/build.sh extract`） | 読むための写し。出典は原本のファイル・章節・頁で書く |

- **全入力を読んでから分解を始める**。Office 原本は抽出テキストで読み、表・図・脚注の抜けが疑われる箇所は原本を確認する。PDF は Read で直接読む（頁番号を出典に使う）
- `docs/00-inputs/` はエージェントが書けない（`INDEX.md` だけ更新する）。抽出に失敗したファイルは INDEX の備考に書き、ユーザーに再提供を依頼する
- 版が複数ある場合は INDEX に版と受領日を書き、最新版を正とする。旧版との差分は §5 の優先順位ルールで扱う

## 2. RFP 概要の把握（rfp-analysis.md §1）

- 発注者、案件名、案件種別、RFP ファイル一覧と版、目的・背景の要約、期限（提案期限・稼働希望時期）、予算、提出物と納期、評価基準を書く
- **モードを判定する**：
  - **モード A（クライアント案件）**：発注者の RFP に基づく受託。既定値
  - **モード B（自社プロダクト）**：RFP が社内の企画書・依頼書である場合。「発注者」は社内の依頼者（事業責任者）と読み替える
- 判定結果と根拠を §1 に書く。以降の質問バンク（`question-bank-client.md`／`question-bank-product.md`）と proposal.md の要否はこの判定に従う

## 3. RFP 要求分解（rfp-analysis.md §3）

### 3.1 分解の単位

- **1 行 1 要求**（原子化）。「A と B を行い、C を報告する」は 3 行に分ける。複合要求のままでは採否と対応 ID が付けられない
- 要約は RFP の意味を変えない。解釈を加えた場合は「判定＝曖昧」にして解釈案を OQ に書く
- **出典**は「ファイル名 §章節 p.頁」で書く（例：`rfp.pdf §3.2 p.12`、`別紙2.xlsx 機能一覧!B14`）。出典の無い行は作らない
- ID は RFP-001 から連番。RFP の記述順に振ってよいが、**記述順を優先順位と見なさない**

### 3.2 区分

| 区分 | 内容 | 要件定義での主な行き先 |
|------|------|----------------------|
| 目的 | 背景・狙い・達成したい状態 | OBJ（§2）→ BZ 目的系 |
| 業務 | 業務の流れ・業務ルール・処理量 | BZ・UC・業務パターン表 |
| 機能 | システムに求める機能・画面・帳票・連携 | BZ 手段系（IT 手段）→ UC・外部 I/F |
| 非機能 | 性能・可用性・セキュリティ・運用性など | NFR（6 カテゴリ） |
| 制約 | 予算・期限・必須／禁止技術・法令・環境 | requirements.md §制約条件・NFR-ENV |
| 移行 | 既存データ・並行稼働・切替 | NFR-MIG・requirements.md §運用・移行 |
| 運用・保守 | 運用体制・サポート・保守範囲 | NFR-OPS・requirements.md §運用・移行 |
| 体制・契約 | 受注者の体制・役割分担・契約条件・検収 | requirements.md §制約・§受入基準。要件の対象外なら「対象外（提案書で回答）」 |
| 提出物 | 提案書・見積・成果物の形式と期限 | document-set.md・Phase 4 の成果物 |

### 3.3 判定

| 判定 | 定義 | 処置 |
|------|------|------|
| 明確 | 解釈が 1 つで、要件に写せる | そのまま要件定義で扱う |
| 曖昧 | 解釈が複数ある／数値・条件が無い（「迅速に」「十分な」） | OQ（種別：RFP 曖昧）。仮の解釈を書き、発注者に確認 |
| 矛盾 | RFP 内部、または資料間で食い違う | OQ（種別：RFP 矛盾）。§5 の優先順位で仮決めし、必ず発注者に確認 |
| 欠落 | 標準構成（§4）にあるが RFP に記載が無い | 行を起こして OQ（種別：RFP 欠落）。MUST 影響のものから聞く |
| 対象外 | 要件定義の範囲外（提案書・契約で回答するもの、後工程の事項） | **理由を必ず書く**。黙って消さない |

- 「要件定義での扱い」列には行き先を 1 つ書く：**BZ／UC／NFR／制約／対象外**（区分が業務でも、扱いは NFR になることがある）
- **「対応 ID」列は Phase 1 では空でよい**。Phase 2 で BZ・UC・NFR の ID を後埋めする（§6）

## 4. 標準構成との突合（欠落チェック。rfp-analysis.md §4）

- `templates/rfp.md` の章立て（案件概要／背景と目的／ステークホルダと対象範囲／業務要件・機能要件／非機能要件／制約条件／運用・移行・公開／成功基準・受入基準／リスク／未決事項／スケジュール・体制・費用／提出物と評価基準／前提・除外条件）をチェックリストとして使う。各章の「記載が無い場合」の注記が OQ 化の目安になる
- 各章について RFP の記載有無（有／一部／無）と該当 RFP-NNN を書く。「無」「一部」は §3 に判定＝欠落の行を起こし、OQ にする
- 非機能 6 カテゴリ（AVL／PERF／OPS／MIG／SEC／ENV）は章単位でなくカテゴリ単位で突合する。RFP の非機能記載は薄いのが普通で、欠落が最も出やすい
- 欠落は「RFP の不備」ではなく**確認すべき事項**として扱う。発注者が「受注者に任せる」と答えたら、既定値（`non-functional-requirements.md` 等）で提案し、合意を decision-log に残す

## 5. 達成目標の抽出と、資料間の優先順位

### 5.1 OBJ-NN（rfp-analysis.md §2）

- RFP の目的・背景から達成目標を抽出し OBJ-01 から振る。**RFP 原文の要約と出典**を必ず併記する（要件定義で新たな経営目的を立てない）
- 測定尺度・目標値が RFP にあれば転記し、KPI-NN を振ってよい。無ければ空欄にし、測定可能な目標は Phase 2 の BZ 目的系（測定尺度・現状値・目標値）で決める
- 目的が書かれていない RFP は、判定＝欠落で OQ にする。目的の無いまま機能一覧だけで要件定義を始めない（中抜けの原因）

### 5.2 資料間が食い違うときの優先順位（仮決めの規則）

| 食い違い | 仮に優先するもの | 処置 |
|---------|----------------|------|
| 本文と別紙 | 本文 ＞ 別紙 ＞ 参考資料 | OQ（RFP 矛盾）で発注者に確認 |
| 新旧の版 | 新しい版 ＞ 古い版 | 差分を INDEX の備考に書き、変更点は OQ で確認 |
| RFP と議事録・口頭の要望 | RFP（書面） | 口頭の要望は RFP 改訂候補として OQ |
| RFP とステークホルダの要求（Phase 2 のヒアリング） | RFP | 要件で黙って上書きしない。OQ（RFP 矛盾）で発注者に確認 |

- 優先順位は**仮決めのための規則**であり、決着ではない。矛盾は**すべて OQ にする**。採った解釈は decision-log に残す
- 原本は書き換えない。発注者の回答で RFP の記述が上書きされたら、INDEX の備考に「RFP §X は OQ-NNN で上書き」と書く

## 6. 要件定義への写像と後埋め（Phase 2）

- Phase 2 の要件定義では、rfp-analysis.md §3 を**作業の入口**として使う。区分＝目的は BZ 目的系、機能は BZ 手段系と UC、非機能は NFR に写す
- 各文書の行が決まったら、§3 の「対応 ID」列に BZ／UC／NFR の ID を書く（複数可）。**全 RFP-NNN に対応 ID か対象外の理由がある状態**を Phase 2 の完了条件にする
- 逆方向も確認する：RFP に源泉を持たない BZ（ヒアリング由来の追加要求）は、business-requirements.md の源泉列に提起者を書き、RFP 範囲外の追加であることを明示する。採否は発注者の合意で決める
- **RFP の全要求を MUST にしない**。RFP は要求であって要件ではない。優先度・採否は business-requirements.md の 6 基準・MoSCoW で決め、発注者の合意を取る。RFP で「必須」と明記された要求を Should 以下にする場合は、理由を OQ にして発注者に確認する
- 対象外にした RFP 項目は、requirements.md §スコープの「やらないこと」にも理由付きで載せる

## 7. ヒアリング計画（rfp-analysis.md §7）

- 質問は「RFP で答えが出ているか」を確認してから作る。RFP に書かれていることを聞き直さない
- 優先順位：① 矛盾 ② 曖昧のうち MUST 候補に影響するもの ③ MUST に影響する欠落 ④ 目的・測定尺度の欠落 ⑤ その他の欠落・曖昧
- 質問先（発注者の誰か）と期限を OQ ごとに決め、1 回のヒアリングで聞く OQ を束ねる（1 ターン 3 問以内の原則は維持する）
- Phase 1 の終わりに PM がユーザーと確認する「優先質問」は、①〜③から最大 5 件を選ぶ

## 8. 要件レビュー（Phase 3）での確認項目

requirements-reviewer は以下を確認する：

| 確認項目 | 不備の重大度 |
|---------|-------------|
| `docs/01-rfp/rfp-analysis.md` が存在し、§3 に全 RFP 要求が出典付きで分解されている | 無ければ Critical |
| 判定＝曖昧／矛盾／欠落の全行に OQ-NNN が付いている | 付いていなければ Critical |
| 全 RFP-NNN に対応 ID か対象外の理由がある（黙って消えた要求が無い） | Critical |
| MUST の BZ・UC が RFP-NNN か発注者合意（D-NNN）に遡れる | Major |
| OBJ-NN が RFP 原文の出典を持ち、要件側で書き換えられていない | Major |
| RFP と矛盾する要件が OQ なしで確定していない | Critical |
| 非機能 6 カテゴリの欠落チェック（§4）が行われている | Major |

## アンチパターン

- **RFP の記述順を優先順位にする**（章の先頭にある要求が重要とは限らない。優先度は 6 基準で決める）
- **全部 MUST にする**（RFP の要求をそのまま要件に昇格させる。採否と発注者合意を経ていない）
- **原本を書き換える**（`docs/00-inputs/` を編集して整合させる。食い違いは OQ と INDEX の備考で扱う）
- **解釈を黙って決める**（曖昧・矛盾を requirements-architect が独断で解決し、OQ を起票しない）
- 抽出テキストだけを読み、表・図・脚注の欠落に気付かない
- 対象外の要求を表から消す（後で「なぜ無いのか」が追えない）
- ヒアリングで聞いた要望を RFP より優先して要件に書く（発注者の確認を経ていない上書き）
- 分解を 1 要求 1 行にせず、複合要求のまま対応 ID を付ける

# 要件定義文書ガイド

Phase 1（RFP 分析）・Phase 2（要件定義）で作る各文書の目的・粒度・完了基準（誰と合意したら完成か）・整合相手を 1 枚にまとめたもの。「フォーマットは合意したが、どこまで書くかで後からもめる」ことを防ぐ。requirements-architect は作成前に、requirements-reviewer は Phase 3 の第 1 パス（文書チェック・集合チェック・整合チェック）で参照する。文書の採否は `docs/99-pm/document-set.md` が正本。

> 出典：IPA『ユーザのための要件定義ガイド 第2版』第 7 章 DD（36 文書）・3.3 文書体系・コラム 8（記載範囲）・事例 9（粒度レベル）・事例 20（形式品質）・事例 25（完了基準）。本ハーネスの文書体系に写像した。

## 3. 粒度の基準

- **要件定義 vs 外部設計**：要件定義は「何を・なぜ」と業務ルール。画面項目・API・テーブル定義は書かない。概念データモデルは「全エンティティ＋主要属性」まで、外部設計で「全属性」
- **業務機能の階層**：レベル 1＝対象業務全体、レベル 2＝主要業務（UC の業務領域）、レベル 3＝UC、レベル 4＝UC 内の手順（シナリオの行）。要件定義はレベル 4 まで書いて合意する（「総論賛成・各論反対」を防ぐ）
- **全件が必要な一覧**：RFP 要求分解、業務要件一覧、UC 一覧、ロール、外部 I/F、OQ、用語。**主要でよいもの**：概念データモデルの属性、状態遷移の対象、CRUD の対象エンティティ
- **後続で全件を補完する関係**を明示する：要件定義の UC 基本フロー（変わる業務中心）→ 後工程の業務フロー（システム化する全業務）
- 記載サンプル（各テンプレートの例示行）で詳細度を合意し、最初の 10 行を書いた時点で粒度を点検する

## 4. 文書間の整合（reviewer の整合チェック）

| チェック | 内容 | Grep の例 |
|---------|------|----------|
| 従属値一致 | 同じ ID に同じ名称（BZ-003 の手段名が requirements.md と business-requirements.md で一致。UC 名が一覧と記述で一致） | `grep -rn "BZ-003" docs/03-requirements` |
| 重複 | 同名の UC・BZ・用語が複数の ID を持っていない | 名称でソートして重複を見る |
| 参照元存在 | UC が参照する BZ・ROLE・用語・NFR が定義されている。requirements.md の MVP スコープが参照する BZ が採用行である。rfp-analysis.md の対応 ID が実在する | 参照 ID を抽出し定義側に存在するか照合 |
| 方向の整合 | 全 RFP-NNN に対応 ID か対象外の理由がある。採用 BZ（IT 手段）に UC か NFR がある（フォワード）。親 BZ の無い UC が無い（バックワード） | `grep -c "^| RFP-" docs/01-rfp/rfp-analysis.md` |
| RFP 整合 | OBJ・KPI・制約の転記が RFP 原文（rfp-analysis.md の出典）と一致。RFP と矛盾する要件に OQ がある | rfp-analysis.md §2・§3 |
| 禁止語 | glossary §4 と writing-rules §4 の語が残っていない | `grep -rnE "ユーザ|顧客|…" docs/03-requirements` |

## 5. 台帳の書式（Office 化の前提）

最終成果物は Markdown から Word／Excel／PowerPoint を自動生成する（Phase 4）。生成が崩れないよう、全文書で以下を守る。

- ID 台帳は Markdown 表で書き、**1 列目を ID（見出しは文字どおり `ID`）**にする。台帳の種類ごとに表を 1 つにまとめ、同種の表は列名を揃える
- 1 セル 1 値を原則にし、セル内改行・結合セルに相当する書き方をしない。複数 ID は「、」区切り
- 冒頭の「この文書について」引用ブロックの**第 1 文は発注者が読める文**にする（Word の付録の導入文に再利用される）。エージェント名・フェーズ・パスなどの社内向けの説明は最初の「。」の後に書く
- `## ✅ Self-Check` と `## 📤 Handoff` は文書の末尾に置く（納品物からは自動で除かれる）
- 図は Mermaid で書く（画像化される）。図だけに情報を置かず、要点は表か本文にも書く

## 6. 文書構成の宣言（requirements.md §0 に書く）

要件定義書の冒頭で、本案件で採用した文書と、各文書がどの文書を参照するかを宣言する。IPA の「成果物関連図」に当たる。

```
requirements.md（正本）
 ├─ 参照：docs/00-inputs/（RFP 原本）／docs/01-rfp/rfp-analysis.md（RFP-NNN・OBJ）
 ├─ business-requirements.md（BZ：問題・課題 → 目的 → 手段。採否）
 │    └─ use-cases.md（UC：採用 IT 手段の振る舞い）
 │    └─ non-functional.md（NFR：6 カテゴリ）
 ├─ permissions-matrix.md（ROLE × UC × ENT）
 ├─ glossary.md（用語・禁止語）
 ├─ open-questions.md（OQ：RFP 矛盾・欠落・曖昧・未決・変更要求）→ decision-log.md
 └─ 後工程（本ハーネスの範囲外）：機能一覧（F ← BZ）／業務フロー／データモデル／テスト（← UC）
```

採用しなかった文書（document-set.md で除外）は、ここに「除外（理由）」として 1 行残す。

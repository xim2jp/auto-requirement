# 非機能要件一覧（docs/03-requirements/non-functional.md）

> この文書について：本書は、システムの可用性・性能・運用・移行・セキュリティ・システム環境に関する要件を、計測可能な値と検証方法とともに一覧にしたものである。requirements-architect が Phase 2 で作成し、Phase 3 で requirements-reviewer が欠落・曖昧語・RFP との整合・運用体制との整合を見る。後工程の方式設計・費用見積り・非機能テスト・監視設計の直接入力になる。
> 関連文書：`requirements-toolkit/references/non-functional-requirements.md`（決め方と既定値の正本）／RFP 分析表（docs/01-rfp/rfp-analysis.md）／要件定義書（requirements.md）／ユースケース一覧（use-cases.md）
> ID：`NFR-<CAT>-NN`。CAT ＝ AVL 可用性／PERF 性能・拡張性／OPS 運用・保守性／MIG 移行性／SEC セキュリティ／ENV システム環境・制約

- **作成日**：YYYY-MM-DD　**作成者**：requirements-architect　**版**：v0.1（draft）
- **値の決め方**：RFP の値を優先する。RFP に無い項目は OQ（RFP 欠落）にし、Tier A 既定値（既定値の一例。non-functional-requirements.md）を提案値として置く。「出所」列に RFP-NNN か「既定値（OQ-NNN／D-NNN）」を書き、既定値と異なる項目には**差分理由**を書く

## 0. ビジネス領域の要求（メトリクスを決める前に確認する意思）

技術的なメトリクスの前に、発注者・経営側の**意思**を要求として確認する。ここが判断に迷ったときの拠り所になり、優先順位の最上位になる。

| 要求の種類 | 確認項目 | 回答（要求） | 出所 |
|-----------|---------|-------------|------|
| 業務特性／サービス時間 | 提供先（企業内／企業間／コンシューマ）、提供地域（国内／国外）、提供時間（通常・特定日）、繁忙期・閑散期、利用者数、拠点・端末数 | | RFP-0xx |
| 業務継続 | 停止を許容できない業務の範囲、計画停止の可否、単一障害時／多重障害時の許容 | | |
| 業務連携 | 外部システム連携の有無と方法（決済／IdP／LINE／AI API） | | |
| 業務量 | 取扱量（件/月）、1 年後・2 年後の拡張見込み（利用者数 × 倍/年） | | RFP-0xx |
| 運用方針／内部統制 | 運用範囲・場所、運用体制（発注者／受注者）、監査証跡の要否 | | RFP-0xx |
| セキュリティ | 個人情報の有無と種類、順守する法令・ガイドライン、第三者診断の要否、セキュリティチェックシート提出の要否 | | RFP-0xx |
| ユーザビリティ | 初心者／顧客向けか熟練者向けか、アクセシビリティ要求、対応言語 | | |

「現行と同じでよい」と言われた項目も、現行の値を書き下ろす（Web 化やクラウド化で意図せず悪化することがある）。

## 7. トレードオフと前提条件

| トレードオフ | 判断 | 理由 | 前提条件（リスクとして管理） |
|-------------|------|------|---------------------------|
| 管理者 MFA 必須 vs 利便性 | MFA 必須 | 管理者は少数で影響が小さい | |
| 稼働率 99.9% 要求 vs 運用体制・費用 | 99.5% で合意（D-NNN） | 守れない SLA は契約リスク | 利用するクラウドの SLA に依存 |

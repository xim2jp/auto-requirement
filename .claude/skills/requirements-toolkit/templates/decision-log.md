# 決定ログ（docs/03-requirements/decision-log.md）

> この文書について：本書は、要件定義の過程で行った判断と確認の内容（要求の採否、RFP の解釈、未決事項の扱い、変更要求の可否）を記録し、「なぜこの仕様になったか」を後から追跡できるようにしたものである。requirements-architect が Phase 1・2 で随時追記する。OQ の回答はここに D-NNN として記録し、open-questions.md の決定列に D-NNN を書く。
> 関連文書：要確認事項一覧（open-questions.md）／RFP 分析表（docs/01-rfp/rfp-analysis.md）／業務要件一覧（business-requirements.md）

- **作成日**：YYYY-MM-DD　**作成者**：requirements-architect　**最終更新**：YYYY-MM-DD

| D-001 | YYYY-MM-DD | RFP 解釈 | RFP-003, OQ-004 | 審査の承認段階 | 2 段階（RFP 本文に合わせる） | 発注者（業務担当） | 確定 |

**ステータス**：仮確定／確定／要再確認

## 2. 詳細記録

判断ごとに以下の形式で書く（§1 の行と同じ ID）。

```

**種別**：（§1 の種別）

**関連 ID**：RFP-… / BZ-… / UC-… / NFR-… / OQ-…（OQ の回答ならここに OQ を書き、open-questions.md の決定列に本 D を書く）

**論点**：
（何について議論したか）

**選択肢**：
- A：...
- B：...
- C：...

**選択**：
（採用した選択肢と理由）

**RFP との関係**：
（RFP のどの記述に沿う／RFP を補う／RFP と異なる。異なる場合は発注者の合意と、INDEX.md の上書き記録）

（この判断が成り立つ前提条件。崩れたら再検討が必要）
```

## 3. 記録のコツ

1. **議論が分岐した瞬間に書く**：「A と言っていたが B に変わった」という変化を残す
2. **却下した選択肢も書く**：なぜ採用しなかったかを残すことで、後の蒸し返しを防ぐ
3. **発言をそのまま引用する**：要約だけだとニュアンスが失われる
4. **「仮確定」と「確定」を分ける**：当日合意したが、後日発注者の上位承認が必要なものは「仮確定」のまま置く
5. **判断者を明記する**：複数のステークホルダがいる場合、誰の決定かを記録する。RFP の解釈・対象外化は発注者の判断とする
6. **捨てた要求・先送りした要求も記録する**：採否の経緯が無いと後で蒸し返される。business-requirements.md の採否列と対応させる
7. **決定済み事項の変更は影響と効果を書く**：当事者間で安易に受け入れず、PM・発注者の判定を経たことを残す（requirements-management.md §3）

要件定義書の各 ID から対応する判断 ID へのリンクを張ると、後のレビューや変更時に追跡しやすい（例：BZ-003 → D-012, D-015）。

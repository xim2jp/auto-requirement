# RFP Authoring Skill

ユーザーが話す構想（数行〜1 ページの「こういうものを作りたい」）を、**要件定義の入力として使える RFP**（`docs/01-rfp/rfp.md`。Office では「要件定義要求書（RFP）」）に仕上げるための知識集。ユーザーは非エンジニアであることを前提にする。

> 位置づけ：本ハーネスの Phase 0（RFP 準備）。ユーザーが RFP を持っていれば Phase 0 は「`docs/00-inputs/` に置く」だけで終わり、このスキルは使わない。

## Phase 0 の流れ

```
0-1 構想を受け取る    PM がユーザーの言葉をそのまま docs/01-rfp/concept.md §1 に記録（00-inputs の資料も読む）
0-2 聞き取り          rfp-writer が質問を作り、PM がユーザーに中継（1 回 3 問・最大 3 回。全問に選択肢と「おまかせ」）
0-3 RFP 起草          rfp-writer が docs/01-rfp/rfp.md を書く（分からない点は推奨値で仮定し、§13 と未決事項に明示）
0-4 ユーザー確認      PM が「RFP の要点」（専門用語なし・1 画面）を見せて OK／修正を受ける → OK で Phase 1 へ
```

## 原則

1. **ユーザーの言葉を正本として残す**。concept.md §1 は原文のまま。RFP の全要求は concept.md の発言か回答（Q-NN）か、明示した仮定（AS-NN）に遡れる
2. **専門用語で聞かない・専門用語で答えさせない**。「非機能要件」ではなく「夜中に止まったら困りますか」。用語の言い換えは `sdlc-toolkit` SKILL.md §9 の表に従う
3. **全問に選択肢と「おまかせ（推奨：…）」を付ける**。「分からない」は正しい回答であり、推奨値で仮定して先へ進む。仮定は RFP §13 と §10 未決事項に必ず書き、黙って決めない
4. **聞きすぎない**。1 回 3 問、最大 3 回。それで埋まらない点は推奨値で仮定する。要件定義（Phase 2）でもう一度確認する機会がある
5. **RFP に書くのは「何をしたいか（要求）」まで**。画面設計・技術選定・作り方は書かない（ユーザーが技術を指定した場合だけ制約として書く）
6. **作らない選択肢を消さない**。既製の SaaS や運用の工夫で足りそうなら、RFP の背景か未決事項にその可能性を書く
7. **背伸びさせない**。少人数・小予算の構想に、24 時間 365 日・高可用性などの過剰な条件を足さない。推奨値は規模に合わせる（`references/concept-interview.md` §4）
8. **RFP は発注者（ユーザー）名義の文書である**。文体は「本システムに求める〜」「〜を求める」。受注者側の視点（提案・見積の書きぶり）を混ぜない

## references / templates

| ファイル | 内容 | 使いどころ |
|---------|------|-----------|
| `references/concept-interview.md` | 構想の聞き取り：最初に必ず確かめる 7 点、質問バンク（選択肢・おまかせ推奨値つき）、規模の見積もり方、推奨値の表、RFP 起草の規則、セルフチェック | 0-2・0-3 の正本 |

| `templates/rfp-document.md` | RFP（要件定義要求書）の本文テンプレート。発注者名義・提出用の文体 | 0-3 で `docs/01-rfp/rfp.md` を書く |
